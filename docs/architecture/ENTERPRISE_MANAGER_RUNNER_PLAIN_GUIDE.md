# CartridgeFlow 企业版架构：大白话说明

> 文档状态：团队讨论稿，不代表当前 Lite 已经实现这些能力。
>
> 阅读对象：产品、研发、合作伙伴，以及第一次了解企业版方向的团队成员。

## 一句话说明

CartridgeFlow 企业版可以先简单理解为：

> 一个统一管理器，管理分散在云端、客户内网和不同服务器上的多个卡带运行器。

统一管理器负责“管”，卡带运行器负责“干”。

```text
                       统一管理器
            管账号、管卡带、管权限、下发任务
                           |
              +------------+------------+
              |            |            |
              v            v            v
          云端运行器     客户 A 运行器   客户 B 运行器
          执行普通任务   访问 A 的系统   访问 B 的系统
              |            |            |
              v            v            v
          公共互联网      A 的 ERP       B 的 CRM
```

## 1. 什么是统一管理器

统一管理器相当于总指挥中心。它自己通常不执行复杂的 AI 流程，而是负责安排和监督工作。

它主要管理：

- 有哪些企业、部门和用户；
- 每个人可以查看或操作什么；
- 平台里有哪些卡带，每张卡带是什么版本；
- 哪张卡带应该部署到哪个运行器；
- 什么时候执行任务，任务是否成功；
- 每次任务由谁发起、用了多少资源、产生了什么结果；
- 运行器是否在线，出现故障后是否需要重试或人工处理；
- 卡带的升级、停用和回滚。

用户看到的企业管理后台，本质上就是统一管理器的操作界面。

## 2. 什么是卡带运行器

卡带运行器相当于执行工人。它接收统一管理器下发的任务，然后真正运行卡带。

它主要负责：

- 接收任务；
- 获取指定版本的卡带；
- 执行卡带里的流程节点；
- 调用 AI 模型、接口、数据库或本地工具；
- 生成日报、文档、图片、视频等产物；
- 持续汇报进度；
- 把结果或真实错误返回统一管理器。

运行器不一定都放在我们的服务器上。它可以部署在：

- 我们自己的云服务器；
- 客户自己的云服务器；
- 客户公司的内网；
- 专门生成视频的 GPU 机器；
- 工厂、门店等边缘设备。

现有 CartridgeFlowLite 已有的卡带执行能力，未来可以逐步整理为这种运行器，不需要全部推倒重写。

## 3. 为什么要把运行器分散部署

很多企业系统只允许在内网访问。例如，客户不可能为了使用一张卡带，就把 ERP 数据库直接开放到公网。

这时可以把运行器放进客户内网：

```text
我们的统一管理器
        |
        | 下发任务，只传必要信息
        v
客户内网中的运行器 ---> 客户 ERP / CRM / 文件系统
        |
        | 返回状态、摘要或经过允许的结果
        v
我们的统一管理器
```

这样做有几个直接好处：

- 客户内部接口不用暴露到公网；
- 敏感数据可以留在客户环境中；
- 不同机器可以承担不同类型的任务；
- 同一套管理器可以统一管理多个客户和多个地点；
- 客户断网或网络不稳定时，运行器可以保留任务状态并继续处理。

## 4. 卡带是什么

卡带是可以被安装、发布和执行的一套业务流程。

例如，一张“AI 科技日报”卡带可能包含：

```text
读取 RSS
  -> 去重和筛选
  -> AI 评分与摘要
  -> 生成日报
  -> 生成视频
  -> 发布到指定平台
```

统一管理器决定这张卡带在哪里运行、何时运行、使用哪个版本；运行器负责把这套流程真正执行出来。

卡带里不应该写死客户密码、服务器地址和生产环境凭据。卡带只描述需要什么能力，具体连接信息由部署环境提供。

## 5. 连接器是什么

连接器是运行器与外部系统之间的翻译员和插头。

例如，卡带只提出“查询客户订单”，但不同企业可能使用不同系统：

```text
卡带：查询客户订单
            |
            v
运行器根据当前客户选择连接器
       /          |          \
      v           v           v
  金蝶连接器   用友连接器    SAP 连接器
```

连接器负责处理：

- 外部系统的地址和接口格式；
- 登录认证和凭据引用；
- 字段名称转换；
- 超时、限流和重试；
- 错误信息转换；
- 哪些操作允许自动执行，哪些必须人工确认。

因此，最容易理解的四个概念是：

```text
统一管理器：决定谁在什么地方执行什么
卡带运行器：真正执行任务
卡带：描述完整业务流程
连接器：帮助卡带安全连接外部系统
```

## 6. 一次任务是怎样运行的

以“每天生成企业经营日报”为例：

1. 统一管理器发现定时时间到了。
2. 统一管理器找到这家企业对应的运行器。
3. 统一管理器告诉运行器：执行经营日报卡带的指定版本。
4. 运行器通过客户的 ERP 连接器读取当天数据。
5. 运行器执行统计、AI 总结和报告生成。
6. 运行器持续向统一管理器汇报进度。
7. 任务成功后，运行器返回产物位置和结果摘要。
8. 统一管理器保存运行记录，并通知有权限的用户。

如果失败，运行器必须返回真实原因，不能用假数据把失败伪装成成功。

## 7. Java 和 Python 应该怎样分工

不需要在 Java 和 Python 之间二选一，也不建议现在把整个 Python 项目重写成 Java。

建议分工如下：

```text
Java / Spring Boot：统一管理器
Python：卡带运行器、AI、数据处理、视频处理
React：Lite 工作台和企业管理界面
```

Java/Spring Boot 更适合统一管理器，因为它在企业登录、权限、数据库事务、后台管理和长期运行服务方面有成熟的工具。

Python 更适合继续承担运行器，因为现有卡带执行能力已经使用 Python，而且 AI、数据处理、FFmpeg 和模型工具生态也更方便。

真正重要的不是两边使用同一种语言，而是它们使用一套稳定的通信协议。统一管理器只下发标准任务，运行器只返回标准进度和结果。

## 8. 第一版企业架构应该做到什么

第一版不要试图一次做成完整企业平台。先完成最小闭环：

1. 运行器能够主动向统一管理器注册，并定期报告自己在线。
2. 统一管理器能够看到运行器列表和状态。
3. 统一管理器能够选择卡带和运行器，下发一次任务。
4. 运行器能够执行任务并返回进度、结果和错误。
5. 统一管理器能够查看历史记录。
6. 每次任务都有唯一编号，重复发送不会造成重复副作用。
7. 管理器与运行器之间有基本身份验证，陌生机器不能接任务。

第一版暂时不需要：

- 拆成大量微服务；
- 一开始就使用 Kubernetes；
- 一开始就建设 Kafka 集群；
- 完整计费系统；
- 连接器市场；
- 一次支持所有企业软件；
- 非常复杂的 RBAC 和审批流。

先让“一个管理器管理两个运行器，并稳定执行一张真实卡带”跑通，再逐步增加企业功能。

## 9. 第一阶段建议界面

企业管理器最初只需要几个核心页面：

- 运行器：查看哪些机器在线、版本和最近心跳；
- 卡带：查看卡带及其版本；
- 部署：决定哪张卡带安装到哪个运行器；
- 任务：发起任务并查看进度；
- 结果：查看产物、错误和运行日志；
- 凭据引用：配置运行器可以使用哪些外部系统身份。

团队在设计新功能时，可以先判断它应该属于“管理器”还是“运行器”，避免两边职责混在一起。

## 10. 必须尽早守住的边界

即使第一版很小，下面这些原则也应该从一开始保留：

- 密钥不能打包进卡带；
- 卡带和部署都要有版本；
- 每次运行都要有唯一任务编号和追踪编号；
- 统一管理器与运行器不能共同随意修改同一套数据库表；
- 客户敏感数据能在本地处理时，就不要传回中央管理器；
- AI 只能调用已明确授权的连接器操作；
- 会产生真实副作用的操作必须支持防重复，必要时加入人工确认；
- 任务失败必须保留真实错误、执行步骤和当时使用的版本；
- 运行器失联不能直接等同于任务失败，也不能直接认定任务成功。

## 11. 当前推荐结论

团队现阶段可以统一使用下面这句话描述企业版：

> CartridgeFlow 企业版由一个统一管理器和多个分散部署的卡带运行器组成。统一管理器负责用户、权限、卡带、部署、任务和审计；运行器靠近客户数据，负责安全执行卡带；连接器负责适配不同企业系统。

技术路线暂定为：

```text
保留 CartridgeFlowLite 作为卡带制作工作台
保留 Python 作为卡带执行基础
新增 Java / Spring Boot 统一管理器
通过稳定协议连接管理器和运行器
先做最小闭环，再按真实客户需求补齐企业治理能力
```

这是一条演进路线，不是要求个人开发者一次完成全部企业功能。
