# n8n 编排取经、个人产品定位与演进报告

## 结论

CartridgeFlow 不应成为 n8n 的替代品或兼容实现。n8n 解决的是通用系统自动化；CartridgeFlow 当前应为个人用户解决 AI 产品的可安装、可运行、可修订、可解释和可交付。

个人版的核心对象不是 Workflow，而是 **可交付产品**：用户安装一张卡带，以自己的输入和资源生产出视频、报告、图集、数据包或可消费的服务结果；每次生产都是独立 revision，而非一次难以复查的流程执行。

本报告只把 n8n 作为编排系统的设计参照，不引入 n8n，不复制其源码，也不兼容其 Workflow JSON。n8n 源码主体采用 [Sustainable Use License](https://github.com/n8n-io/n8n/blob/master/LICENSE.md)，不是无条件的 OSI 开源许可；其许可对分发和商业托管等使用有约束。CartridgeFlow 保持完全独立实现，以保留自身产品、分发和商业化的选择权。具体商业法律结论在发布前仍须由法务核验。

## 产品定位：个人优先，交付优先

近期目标是个人创作者、独立开发者和小团队，而不是企业控制台。产品承诺应收敛为：

> 将一套 AI 生产过程封装为能在用户资源边界内稳定运行、留下版本证据并交付实际结果的卡带产品。

| 维度 | n8n 的主对象 | CartridgeFlow 个人版的主对象 |
| --- | --- | --- |
| 用户得到的东西 | 自动化工作流及其执行结果 | 可安装的卡带产品及其交付 revision |
| 成功判定 | 工作流节点按规则结束 | 主产物、附件、质量门槛和交付状态均满足 |
| 核心体验 | 连接系统、配置自动化 | 选择产品、提供输入、生产、检查、下载或继续修订 |
| 资产沉淀 | 工作流配置和凭据 | 卡带版本、输入版本、产物、摘要、运行 trace 和资源放置记录 |
| 付费基础 | 通用自动化能力 | 云端生产资源、产物存储、计划运行、高价值卡带和更强的交付保障 |

截图中的“产品详情”应成为这一定位的事实界面：主产物、同次附件、交付状态、卡带版本、输入版本、Runner、外部调用、失败恢复和新 revision 都可见。`再次运行` 的真实语义应是“以当前或新输入生产新 revision”，绝不覆盖既有交付物。

个人版不做多租户、组织级权限、企业审计控制台或全量连接器市场。它需要先证明一件事：用户无需理解复杂 Flow，也可以稳定得到自己要的结果，并知道结果是如何产生的。

## 当前判断

当前 Root Flow 已具备流程图、协议校验、检查点、人工交互、错误信封和恢复入口，但执行模型仍是一次性串行状态机：

- `RootFlowEngine` 以队列推进并跳过已访问状态，节点在一次运行中不能自然重复执行。
- 控制分支可以产生多个后继，但合流没有 `all`、`any` 或按键匹配的显式语义。
- 工程画布展示 `action_route`、`failure_route`，运行调度只消费常规控制和分支边。
- 数据边已用于分析和展示，运行时数据仍主要通过共享 `context.store` 传递。
- 画布预留了 `sub_flows`，但尚无实际子 Flow 运行能力。

因此，当前优先级不是增加节点类别，而是让 Flow 的可视结构、协议合同和真实执行形成同一套语义。

## 从 n8n 借鉴什么

| n8n 已验证的做法 | CartridgeFlow 的独立实现方向 |
| --- | --- |
| 执行栈、节点运行记录和等待输入 | 使用 `ExecutionPlan` 和可持久化 token 调度；token 记录 run、node、attempt、输入值引用和 checkpoint。 |
| 逐项处理、批量处理与等待 | 不采用隐式 item 魔法；用显式 `map`、`batch`、`loop`、`wait` 节点声明上限、并发、顺序和退出条件。 |
| 子工作流与稳定输入输出 | 只支持卡带内的 `id + version + interface digest` 引用，禁止 URL、任意 JSON 和跨卡带动态加载。 |
| Pin/Mock 数据与局部执行 | 保存脱敏 fixture、来源和 schema digest；局部执行必须计算依赖闭包，并对外部副作用默认隔离。 |
| 节点版本化 | 卡带固定节点、工具与子 Flow 的版本；新版本通过明确迁移，历史运行和历史产物可复现。 |
| 节点错误输出 | 正常、失败、补偿和人工恢复均为可执行、可视、可测试的边，而不是 UI 推测。 |

n8n 的循环、数据 pin/mock 与节点版本化是成熟参考，但其通用数据自动迭代、动态表达式和 Code Node 不适合直接成为 CartridgeFlow 的基础语义。

## 差异化原则

1. **交付优先**：Flow 的成功不是“节点跑完”，而是主产物、质量门槛、交付状态和 revision 均满足交付契约。
2. **显式而非猜测**：控制、数据、失败、资源、补偿和工具内部步骤分别声明，前端不得从名称或自然语言推断。
3. **副作用可治理**：每个写入、网络调用、命令和外部变更都声明 effect、permission、idempotency、retry、compensation 和 replay policy。
4. **值可追溯**：输入、节点输出和 Artifact 使用 schema、digest、producer 与 lineage 关联，`store` 仅作运行缓存。
5. **卡带可演进**：卡带、子 Flow、工具合同和产物互相绑定版本；升级、回滚、卸载不破坏既有运行证据。

目标分层：

```text
Cartridge delivery contract
  -> Root Flow (用户可理解的业务阶段)
  -> Execution Plan (fork/join/map/loop/wait/failure 的调度语义)
  -> Tool operation graph (DLC/MCP 的内部步骤与 fallback)
  -> Local resource binding (本机凭据、端点与受控能力)
```

## 后续方向：遗留接口适配，但不提前做企业版

“探针卡带 + 知识库 + 可变形适配接口”是有价值的后续方向。它不是现在要做的企业功能，而是可以从个人开发者场景开始验证的下一层产品能力：开发者导入自己有权使用的接口文档、样本、调用日志和 fixture，由卡带形成可审查的接口事实，再把稳定的新合同映射到不可修改的旧接口。

该方向的正确产品模型如下：

```text
已授权证据（文档 / 样本 / 日志 / fixture）
  -> 接口事实库（来源、置信度、字段语义、风险）
  -> 人工确认的适配合同（输入 / 输出 / 映射 / effect）
  -> 本地适配卡带（验证 / 影子运行 / 版本化发布）
```

“可变形”只能发生在受版本控制的适配层，不能是运行时任意猜测：它必须声明字段映射、鉴权、超时、幂等、错误映射、副作用、重放边界和回滚方式。探针也应先是被动的事实采集，主动调用只允许在明确授权、限流和安全隔离下进行。这样才能逐步形成未来企业用户真正会为之付费的能力，而不是把不确定推断包装成“无损接入”。

这条路线与 n8n 的差异尤其清楚：n8n 可编排已知接口；CartridgeFlow 的潜在价值是把不清晰、不能改的接口，转化为带证据、可测试、可追溯的产品能力。前提是先在个人本地适配场景中验证，不能以企业愿景替代产品闭环。

## 推进任务与验收

### PRODUCT-001: Product Delivery Contract v1

定义产品、主产物、附件、质量门槛、交付状态和 revision 的运行时事实。验收：运行成功、产物生成和完成交付为三个可区分状态；任何状态都能定位卡带、输入、资源和运行证据。

### PRODUCT-002: 产品运行记录与产物视图

把产品页做成真实的交付台账。验收：主产物、附件、摘要、下载、卡带版本、输入版本、Runner、耗时、失败/重试和新 revision 都可追溯；新运行不会覆盖已有产物。

### PRODUCT-003: 本地/云端 Runner 放置策略

让个人用户可以理解并选择计算和数据的位置。验收：每次运行记录本地或云端 Runner、外部调用和成本归属；敏感输入或本地资源不能因云端运行被静默上传。

### ORCH-001: ExecutionPlan v1

冻结控制边、合流、循环、等待和失败边的规范；让画布、Analyzer 和运行器消费同一份计划。验收：每种边都有正反 conformance 用例，未声明循环、隐式合流和无法执行的可视边均被阻止。

### ORCH-002: Token 执行器

以 token 替换全局 `visited` 调度。验收：可重入循环、批量、并行上限、暂停恢复和 checkpoint 重放均具有确定性的事件 trace；副作用 token 不会自动重放。

### ORCH-003: 类型化值与端口

引入值引用和端口合同。验收：每个输入可定位 producer；schema、敏感级别与 digest 不匹配在执行前阻止；分支和合流不会通过共享可变数据改变彼此结果。

### ORCH-004: 卡带内子 Flow

实现封闭的可复用过程模块。验收：子 Flow 的接口变更必须产生新版本；调用、失败、取消、检查点和 Artifact lineage 可跨边界追踪；跨卡带动态执行被拒绝。

### ORCH-005: Fixture 与局部执行

把 TestBench 从手工探针升级为可复用测试资产。验收：可保存脱敏 fixture、选择节点进行依赖闭包执行、比较输出和产物，并保证 fixture 不在生产运行生效。

### ORCH-006: 可见失败与恢复线路

统一正常、失败、补偿、人工审批和恢复路径。验收：所有副作用节点都有可见权限、重试和回滚边界；运行 trace 可定位到节点、attempt、operation 和 Artifact。

### ADAPT-001: 接口事实采集模型

为未来适配能力定义证据和确认机制。验收：接口文档、样本、日志和 fixture 均能标注来源、脱敏策略、置信度和人工确认；未授权主动扫描不能进入执行路径。

### ADAPT-002: 可版本化适配合同

让新旧接口之间的转换成为可测试的卡带资产。验收：合同明确输入/输出、字段映射、鉴权、幂等、错误、effect 和回放边界；个人本地环境可用 fixture 完成验证，暂不引入企业版治理面。

## 明确不做

- 不做通用连接器市场、Cron/Webhook 自动化平台或 n8n Workflow 兼容层。
- 不做任意代码节点、无约束动态表达式或无法静态解释的业务分支。
- 不把远程 MCP 或外部系统伪装为透明工具；它们必须诚实标记透明度和能力边界。
- 不以更多节点或更复杂画布替代执行语义、测试证据和交付闭环。
- 当前不做多租户、企业组织管理、集中式审计控制台或“自动摸清所有遗留接口”的承诺。

## 完成标准

先完成两张独立的个人产品卡带：用户可以安装、提供输入、预检、生产、查看主产物与附件、建立新 revision、局部测试、失败恢复和下载交付物；每一步都可由协议、trace 和自动测试证明。

在此之后，再以一张本地接口适配卡带验证“导入已授权证据 -> 人工确认合同 -> fixture/影子验证 -> 版本化适配”的最小闭环。只有该闭环成立，才讨论企业级私有 Runner、审批和治理能力。
