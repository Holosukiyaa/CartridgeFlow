## 1. 文档目的

本文档用于指导 CartridgeFlow 企业方向中第一个真实接入环节的产品和技术实施。

需要解决的不是“扫描并理解客户整个旧系统”，而是：

```text
针对客户准备扩展的一个具体功能，
找到掌握相关接口的一到两名负责人，
通过结构化交互获取他们掌握的知识，
再用最少、受控、可审计的探测进行验证，
把验证结果保存为客户本地知识，
最后生成经过负责人批准、可供运行器正式使用的连接绑定。
```

本文档同时承担以下职责：

- 固定产品边界，避免演变成独立的全量系统扫描产品；
- 固定客户数据只能保存在客户本地的原则；
- 固定“口述知识不能直接等于正式事实”的验证原则；
- 固定“候选知识不能静默覆盖正式知识”的治理原则；
- 固定官方卡带、运行器探针、MCP 工具和本地知识库的职责；
- 给出最小可用版本、实施顺序和验收门槛；
- 为后续真实客户项目留下按证据扩展的空间。

## 2. 已经确定的产品结论

以下结论作为当前设计基线。没有真实项目证据时，不应随意扩大范围。

### 2.1 不做独立体检软件

“体检”不是独立产品，也不是新的部署层。它是运行器内部的一组受控能力，由官方卡带组织使用。

### 2.2 官方卡带的正式定位

官方卡带建议命名为：

> 接口接入验证卡带

团队内部可以称为“体检卡带”或“探针卡带”，但面对客户时应强调“接入验证”，避免让客户误以为平台会扫描整个系统。

### 2.3 只检查当前功能所需范围

目标不是获得接口的“一切信息”，而是获得：

> 当前业务功能可靠、安全上线所必需的全部接口信息。

### 2.4 主要与接口负责人直接交互

旧项目的知识通常没有完全消失，而是集中在一到两名实施、开发、运维或业务负责人脑中。产品的任务是把这些零散知识快速转化为可验证、可复用的结构化资产。

### 2.5 客户知识只保存在客户本地

接口地址、字段含义、数据库结构、日志、样例、凭据、报告和项目知识默认不得进入厂商云端。

### 2.6 MCP 是访问方式，不是知识库

MCP 工具用于让官方卡带安全访问本地知识库和探针能力。真正的知识需要由客户本地的结构化存储负责。

### 2.7 每次执行只能增加候选认知

一次新观察不能直接修改已经批准的正式知识。必须经过证据比较、测试和必要的负责人确认，才能晋升为正式知识。

### 2.8 先验收连接，再让业务卡带使用

业务卡带不得直接使用尚未批准的接口猜测。只有生成正式 `Connector Binding` 并完成验收后，运行器才允许生产任务调用。

### 2.9 企业级权限治理属于后续阶段

完整组织、RBAC、ABAC、审批编排和配额系统放在接入闭环之后。但第一版仍必须具备最小身份、授权范围、负责人确认和审计能力。

## 3. 问题背景

### 3.1 旧项目的真实状态

企业旧系统常见情况包括：

- 系统仍然稳定运行，但当年的开发人员已经离职；
- 接口文档存在，但与当前生产版本不一致；
- 客户只知道“以前这样调用过”，不知道完整原因；
- 字段名称无法表达真实业务含义；
- 同一个状态值在不同模块中意义不同；
- 某些接口有隐含顺序、缓存、权限或副作用；
- 出错后只能通过历史日志和少数负责人经验定位；
- 软件原厂、实施方、客户 IT 和业务人员之间责任边界模糊；
- 为一个小功能组织完整对接团队，沟通成本可能高于开发成本。

### 3.2 当前交付模式的问题

传统对接往往是：

```text
提出需求
  -> 找原厂
  -> 找实施人员
  -> 找客户 IT
  -> 找业务负责人
  -> 反复开会
  -> 临时写代码
  -> 手工测试
  -> 上线
  -> 资料再次散失
```

CartridgeFlow 希望将其压缩为：

```text
提出具体功能
  -> 确认接口负责人
  -> 官方卡带结构化提问
  -> 本地运行器最小探测
  -> 自动形成测试和报告
  -> 负责人验收
  -> 本地知识沉淀
  -> 生成正式绑定
```

### 3.3 产品机会

产品价值不在于替代负责人，而在于：

- 减少负责人重复解释相似接口；
- 把口述和零散资料转化为结构化知识；
- 用真实证据发现文档和系统行为之间的差异；
- 对十几个相似接口复用已经验证的共同模式；
- 把一次项目交付沉淀为以后可复用的客户本地资产；
- 防止人员变动后再次失去接口知识。

## 4. 产品定义与边界

### 4.1 产品定义

接口接入验证卡带是一张由 CartridgeFlow 官方维护的系统卡带。它运行在客户本地运行器中，围绕一个已明确的业务扩展目标，与接口负责人交互，组织最小探测、测试、知识记录、报告和验收，并在批准后生成正式连接绑定。

### 4.2 输入

最小输入包括：

- 当前需要扩展的业务功能；
- 预计涉及的系统；
- 已知接口或数据来源；
- 接口负责人；
- 客户允许的探测环境；
- 客户允许的接口、地址和操作范围；
- 负责人提供的文档、样例或说明；
- 测试凭据引用，不包含明文凭据。

### 4.3 输出

最小输出包括：

- 接口候选清单；
- 已确认和未确认问题清单；
- 探测计划及批准记录；
- 探测证据；
- 请求与响应契约；
- 字段字典；
- 错误和副作用说明；
- 自动化测试用例；
- 接入验证报告；
- 客户负责人验收记录；
- 正式连接绑定或拒绝上线结论。

### 4.4 明确不做

第一阶段明确不做：

- 自动扫描客户全部内网地址；
- 自动读取整个数据库；
- 自动分析与当前功能无关的系统模块；
- 自动破解、反编译或绕过访问控制；
- 未经批准调用写入或删除接口；
- 自动把客户知识上传到厂商云端；
- 把一次响应直接学习为正式规则；
- 用 AI 猜测替代负责人验收；
- 承诺理解旧系统的全部历史；
- 建设跨客户共享的原始项目知识库。

## 5. 核心设计原则

### 5.1 业务目标先于接口探索

没有明确业务目标，不发起探测。先确定“要新增什么功能”，再倒推需要哪些接口和字段。

### 5.2 最少采集

只读取当前接入所需的最小范围。任何新增探测项都必须说明目的。

### 5.3 负责人优先

已知问题优先向负责人询问，不用无边界扫描代替沟通。

### 5.4 证据优先

负责人说明、旧文档和 AI 推断都可以成为线索，但正式结论必须尽可能有测试、日志、样例或运行行为证据。

### 5.5 结构化优先

核心知识必须以结构化对象保存。向量检索只能辅助搜索，不能成为唯一事实来源。

### 5.6 客户本地优先

客户项目知识、凭据和业务数据默认只保存在客户环境。

### 5.7 候选与正式分离

新发现先进入候选区，不能自动污染正式知识和生产绑定。

### 5.8 确定性执行

AI 负责理解、提问、归纳和提出测试方案；真正的接口调用由受限、确定性的工具执行。

### 5.9 失败保持真实身份

连接失败、权限不足、响应异常、信息不足和负责人拒绝必须保留真实状态，不能用 Mock 或默认值伪装成功。

### 5.10 高风险必须升级确认

写入、删除、审批、支付、发货、库存和权限变更等高风险操作，即使接口相似，也不得仅凭历史模板自动批准。

## 6. 总体架构

```text
客户本地管理器
  ├─ 接入项目管理
  ├─ 负责人交互与审批
  ├─ 客户本地知识库
  ├─ 报告与证据存储
  └─ Connector Binding Registry
              |
              | 下发接入验证任务
              v
客户本地卡带运行器
  ├─ 官方接口接入验证卡带
  ├─ 受控探针执行器
  ├─ MCP Client
  ├─ 普通业务卡带
  └─ 运行日志与检查点
              |
              v
客户本地 MCP 服务
  ├─ knowledge.* 知识工具
  ├─ probe.* 探测工具
  ├─ evidence.* 证据工具
  ├─ test.* 测试工具
  └─ binding.* 绑定工具
              |
              v
目标 OA / ERP / CRM / 数据库 / 文件系统
```

厂商云端不参与客户项目知识处理：

```text
CartridgeFlow 厂商服务中心
  ├─ 软件许可证
  ├─ 官方卡带签名与更新
  ├─ 运行器版本更新
  └─ 客户主动选择的脱敏支持信息
```

## 7. 部署与数据边界

### 7.1 推荐默认部署

对于国内中小企业，推荐使用客户本地一体化部署：

```text
客户服务器
  ├─ 本地管理器
  ├─ 本地知识库
  ├─ 本地凭据库
  ├─ 卡带运行器
  └─ MCP 工具服务
```

初期可以部署在同一台服务器，但逻辑职责必须分开，以便未来拆分。

### 7.2 可选混合部署

管理页面或许可证服务可以在云端，但以下内容仍然保存在客户本地：

- 系统地址和内部拓扑；
- 接口和数据库 Schema；
- 请求、响应与日志正文；
- 字段含义和业务规则；
- 客户人员信息；
- 测试证据；
- 项目知识；
- 密钥和凭据；
- 正式连接绑定中的敏感参数。

### 7.3 完全离线部署

高敏感客户应允许：

- 离线许可证；
- 离线安装包；
- 签名卡带离线导入；
- 本地模型；
- 禁止任何厂商遥测；
- 由客户人工导出脱敏支持包。

### 7.4 数据离开本地的判断

调用外部大模型同样属于数据离开本地。运行器必须明确显示：

- 将发送哪些内容；
- 发送给哪个模型提供商；
- 是否经过脱敏；
- 是否包含接口地址、字段名或业务样例；
- 客户是否已授权。

## 8. 参与角色与责任

### 8.1 需求负责人

说明希望扩展的业务功能和验收结果，不要求其解释技术接口。

### 8.2 接口负责人

掌握目标接口、系统配置、历史调用或业务字段含义。主要负责：

- 回答官方卡带的问题；
- 提供允许使用的资料和样例；
- 确认接口的真实用途；
- 解释业务字段和状态；
- 确认探测计划；
- 审核探测报告。

### 8.3 系统负责人

对目标系统的安全、生产影响和最终接入负责。中小企业中可能与接口负责人是同一人。

### 8.4 接入实施人员

配置运行器、MCP 工具、凭据引用和网络白名单，处理自动化无法解决的技术问题。

### 8.5 卡带设计者

声明业务卡带需要的能力、输入输出和副作用，不直接写死客户接口地址和凭据。

### 8.6 审批人

确认报告是否足以进入正式运行。第一版可以由接口负责人兼任，但系统必须记录审批身份。

### 8.7 AI

AI 是辅助角色，不是责任主体。AI 可以整理、比较、提问和提出测试，但不能替客户承担生产批准责任。

## 9. 核心领域对象

以下对象是未来协议和实现的候选基础。第一版可以缩减字段，但不能混淆语义。


### 9.4 Interface Candidate

```text

system_ref

endpoint_ref
purpose
source
confidence

```

### 9.5 Claim

一条需要验证的知识声明，例如“status=3 表示审批完成”。

```text

subject

value
source_refs
confidence
status
valid_from

```

### 9.6 Evidence

```text

type
source
```

### 9.7 Open Question

```text

answer

answered_at
status
```

### 9.8 Probe Plan

经过批准的最小探测计划。

```text

purpose
operations
allowed_targets
allowed_methods
credential_ref
data_limits
side_effect_policy
approved_by

```

### 9.9 Probe Execution

```text

status

```

### 9.10 Test Case

可重复执行的验证用例。

```text
test_case_id
name
environment_requirement
preconditions
input_fixture_ref
expected_contract
expected_side_effect
cleanup_or_compensation
risk_level
```

### 9.11 Knowledge Item

客户本地知识库中的最小知识单元。

```text
knowledge_id
project_id
scope
content_type
structured_content
status
confidence
evidence_refs
approved_by
version
```

### 9.12 Probe Report

探测结果和上线建议的不可变版本快照。

### 9.13 Connector Binding

业务卡带能力角色与客户具体接口操作之间的正式映射。

```text
binding_id
binding_version
capability_role
connector_operation
input_mapping
output_mapping
credential_ref
policy_ref
verified_report_ref
status
```

## 10. 知识分层与客户本地知识库

### 10.1 第一层：官方通用知识

由 CartridgeFlow 官方维护，可以公开分发：

- HTTP、REST、SOAP、GraphQL 等协议知识；
- 常见认证方式；
- 分页、限流、超时和重试模式；
- 幂等和副作用判断方法；
- 常见错误分类；
- 接口测试方法；
- 报告模板和提问模板。

### 10.2 第二层：接口家族模板

来自合法公开资料、客户授权沉淀或独立研发的通用模板：

- 某类 OA 审批接口的共同形态；
- 某类 ERP 查询接口的分页模式；
- 某版本产品的公开认证方式；
- 通用字段候选映射。

不得包含可识别具体客户的地址、数据、账号、日志或业务规则。

### 10.3 第三层：客户项目正式知识

只保存在客户本地：

- 经负责人和证据确认的接口用途；
- 字段和状态含义；
- 已验证请求与响应契约；
- 已知错误和限制；
- 正式测试用例；
- 已批准连接绑定。

### 10.4 第四层：客户项目候选知识

新观察、AI 推测、未确认负责人说明和差异发现进入候选区，不得直接影响生产绑定。

### 10.5 第五层：运行观察

运行时只记录允许保留的元数据和证据引用，例如：

- Schema 是否发生变化；
- 新错误码是否出现；
- 响应耗时是否异常；
- 正式绑定是否仍满足契约。

默认不把完整生产业务数据长期写入知识库。

### 10.6 存储建议

第一版优先使用结构化数据库保存事实、状态、证据引用和版本。全文检索或向量检索仅作为辅助：

```text
结构化数据库：事实、状态、关系、版本、审批
对象存储：文档、脱敏样例、报告、证据快照
全文检索：文档和历史问题查找
向量检索：相似问题和相似接口推荐
```

## 11. 知识可信状态与生命周期

### 11.1 基础可信状态

```text
UNKNOWN       当前未知
DECLARED      负责人或文档声明，尚未验证
OBSERVED      从一次或多次真实行为中观察到
INFERRED      AI 或规则根据证据推断
CONFLICTED    不同来源互相冲突
VERIFIED      已通过定义好的测试验证
APPROVED      已由负责人批准用于正式绑定
STALE         系统或接口变化后可能已经过期
REJECTED      已确认错误或禁止使用
```

### 11.2 状态晋升

推荐的正常路径：

```text
UNKNOWN
  -> DECLARED
  -> OBSERVED
  -> VERIFIED
  -> APPROVED
```

AI 推断路径：

```text
OBSERVED
  -> INFERRED
  -> 补充测试或负责人回答
  -> VERIFIED
  -> APPROVED
```

冲突路径：

```text
DECLARED / OBSERVED
  -> CONFLICTED
  -> 生成问题或新测试
  -> VERIFIED 或 REJECTED
```

变化路径：

```text
APPROVED
  -> 发现版本或契约变化
  -> STALE
  -> 重新验证
  -> APPROVED 或 REJECTED
```

### 11.3 正式知识不可静默覆盖

任何对 `APPROVED` 知识的修改都必须：

- 创建新版本；
- 保留旧版本；
- 说明变化原因；
- 关联新证据；
- 重新执行受影响测试；
- 必要时重新批准；
- 明确哪些连接绑定受到影响。

## 12. 端到端接入流程

### 阶段 A：定义业务目标

1. 需求负责人描述要扩展的具体功能。
2. 卡带设计者将功能转化为 `Required Capability`。
3. 系统生成最小数据和操作需求。
4. 若目标仍然模糊，不允许进入接口探测。

阶段输出：

- 业务目标；
- 成功标准；
- 需要的能力角色；
- 允许和禁止的副作用。

### 阶段 B：确定接口负责人和范围

1. 客户指定一到两名接口负责人。
2. 负责人确认目标系统和可能接口。
3. 创建接入项目。
4. 明确测试环境、允许地址、凭据和数据范围。

阶段输出：

- 负责人；
- 目标系统引用；
- 范围声明；
- 初始资料；
- 权限边界。

### 阶段 C：结构化交互

1. 官方卡带阅读现有资料。
2. 从业务能力倒推最少问题。
3. 对已有知识不重复询问。
4. 对相似接口先提出候选答案，让负责人确认差异。
5. 将回答保存为 `DECLARED`，不直接批准。

阶段输出：

- 接口候选；
- 字段候选；
- 负责人声明；
- 未决问题；
- 初步风险。

### 阶段 D：生成并批准探测计划

1. 官方卡带生成逐项探测计划。
2. 每项必须说明目的、目标、方法、数据范围和风险。
3. 探测执行器检查白名单和凭据权限。
4. 接口负责人或系统负责人批准计划。

阶段输出：批准的 `Probe Plan`。

### 阶段 E：执行最小探测

1. 运行器调用受控 MCP 工具。
2. MCP 工具执行确定性检查。
3. 所有请求和结果形成审计记录。
4. 敏感内容在保存前脱敏或只保存哈希与引用。
5. 失败保持真实状态。

阶段输出：

- 探测执行记录；
- 证据；
- 新观察；
- 错误；
- 未决问题更新。

### 阶段 F：执行仿真与验证

1. 先执行结构契约测试。
2. 再使用测试环境或脱敏样例验证。
3. 只读接口可以在批准后做生产只读验证。
4. 写接口必须使用沙箱、测试单据、Dry Run 或明确补偿方案。
5. 记录每项结论的实际验证等级。

阶段输出：测试结果和可信状态。

### 阶段 G：生成报告

报告必须同时展示：

- 已确认内容；
- 尚未确认内容；
- 文档、负责人说法和真实行为的差异；
- 已运行的测试；
- 未运行的测试；
- 可安全自动执行的操作；
- 需要人工确认的操作；
- 不建议上线的风险。

### 阶段 H：负责人验收

负责人逐项确认：

- 字段含义；
- 状态含义；
- 副作用；
- 错误处理；
- 测试范围；
- 未知项是否可接受；
- 是否允许进入正式绑定。

### 阶段 I：生成正式绑定

只有验收通过后，才能：

- 固定接口操作版本；
- 固定输入输出映射；
- 关联凭据引用；
- 关联策略和测试；
- 发布 `Connector Binding`；
- 允许业务卡带使用。

### 阶段 J：正式运行和增量观察

正式运行只产生运行观察和候选知识。发现差异时，触发重新验证，而不是直接自我修改。

## 13. 负责人交互设计

### 13.1 交互目标

让负责人用自己熟悉的语言说明过去如何使用接口，不要求其重新编写完整文档。

### 13.2 提问顺序

建议按以下顺序提问：

1. 这个接口以前解决什么业务问题？
2. 谁在什么情况下调用它？
3. 当前准备扩展的功能与过去用法有什么不同？
4. 是否有现成文档、样例、日志或代码？
5. 使用什么认证和权限？
6. 哪些参数必填？
7. 哪些字段最容易误解？
8. 成功和失败分别如何判断？
9. 重复调用会发生什么？
10. 是否会修改真实业务数据？
11. 是否有测试环境和测试数据？
12. 哪些问题负责人自己也不确定？

### 13.3 动态减少问题

如果本地知识库已经存在经过验证的共同规则，官方卡带不应重复开放式询问，而应使用差异确认：

```text
已验证的相似接口都使用 token 认证。
当前接口是否相同？

[相同] [不同] [不确定]
```

### 13.4 问题必须说明原因

每个问题都应该告诉负责人：

- 为什么需要知道；
- 不知道会带来什么风险；
- 系统已有的候选答案是什么；
- 负责人需要回答到什么程度。

### 13.5 不允许诱导确认

AI 不能通过肯定语气诱导负责人接受推测。对于低可信结论必须明确显示“尚未验证”。

### 13.6 回答来源

每个回答记录：

- 回答人；
- 回答时间；
- 原始回答；
- AI 结构化结果；
- 回答人是否确认结构化结果；
- 关联资料和证据。

## 14. 最小探测计划

### 14.1 由能力需求倒推

探测计划必须从 `Required Capability` 生成，不允许从“系统里可能有什么”出发。

例如能力是：

```text
查询某人指定时间范围内的未完成审批
```

最小检查可能只有：

- 接口是否可访问；
- 认证是否有效；
- 人员标识使用哪个字段；
- 时间范围参数格式；
- 状态字段和未完成状态集合；
- 分页规则；
- 空结果和错误结果；
- 响应耗时；
- 是否只读。

### 14.2 每个探测项必须包含

```text
目的
目标接口
请求方法
允许参数
允许数据范围
使用环境
凭据引用
预期结果
风险等级
是否有副作用
失败时是否重试
超时后的处理
证据保存方式
```

### 14.3 白名单

运行器只允许访问探测计划明确批准的：

- 主机；
- 端口；
- 协议；
- 路径；
- HTTP 方法或数据库操作；
- 文件路径；
- 数据表和字段；
- 请求次数和时间窗口。

### 14.4 查询上限

所有探测必须有硬性限制：

- 最大请求数；
- 最大响应体积；
- 最大数据库行数；
- 最大执行时间；
- 最大并发数；
- 最大重试次数；
- 最大证据保留量。

## 15. 探针能力与安全约束

### 15.1 探针是运行器内部能力

探针不是独立可随意运行的软件。它只能由受信任的官方卡带通过受限工具调用。

### 15.2 第一版允许的探针能力

- TCP/HTTP 可达性检查；
- TLS 和证书基本信息；
- 受限 HTTP 请求；
- 受限数据库只读查询；
- 请求与响应 Schema 提取；
- 响应头、状态码、耗时和体积记录；
- 脱敏样例比较；
- 认证是否有效的最小检查；
- 分页、空结果和错误结构验证；
- 已批准测试用例执行。

### 15.3 第一版禁止的探针能力

- 任意端口扫描；
- 任意目录遍历；
- 未授权数据库枚举；
- 自动发现全部内网服务；
- 自动获取或替换凭据；
- 绕过验证码、权限或安全控制；
- 未批准的写入、删除和审批操作；
- 自动执行负责人提供的未知脚本；
- 将接口响应中的指令当成系统授权；
- 自动扩大白名单。

### 15.4 AI 与执行器隔离

AI 生成的是结构化探测建议。执行器必须再次做策略校验：

```text
AI 建议
  -> Schema 校验
  -> 目标白名单校验
  -> 方法白名单校验
  -> 数据限制校验
  -> 副作用校验
  -> 人工批准校验
  -> 确定性执行
```

## 16. 仿真、测试和真实验证

### 16.1 验证等级

建议定义以下等级：

```text
L0 文档检查
仅证明资料中存在相关描述。

L1 结构仿真
使用 Mock 或固定样例验证字段映射和流程结构。

L2 测试环境真实调用
使用客户测试环境和测试数据验证真实接口行为。

L3 生产只读验证
在批准范围内验证生产环境真实查询行为。

L4 生产受控写入验证
使用测试单据、人工确认、Dry Run 或补偿措施验证副作用操作。
```

### 16.2 禁止混淆验证等级

Mock 成功只能记录为 L1，不能描述为“生产接口验证通过”。报告必须逐项展示实际达到的等级。

### 16.3 写入接口验证要求

写入接口至少明确：

- 是否幂等；
- 如何防止重复写入；
- 超时后如何查询真实结果；
- 是否有撤销或补偿接口；
- 测试数据如何清理；
- 是否需要人工确认；
- 失败后是否允许自动重试。

### 16.4 验证证据

每次测试保存：

- 测试用例版本；
- 环境；
- 输入摘要；
- 输出摘要；
- 请求和响应哈希；
- 脱敏证据引用；
- 执行时间；
- 执行者；
- 结果；
- 清理或补偿结果。

## 17. MCP 工具设计

### 17.1 设计定位

MCP 是官方卡带访问本地能力的受控工具层，不负责自行决定业务范围。

### 17.2 Knowledge 工具

建议最小集合：

```text
knowledge.search
knowledge.get
knowledge.list_related
knowledge.record_candidate
knowledge.compare
knowledge.mark_conflict
knowledge.propose_promotion
```

约束：

- 不提供无审批的 `knowledge.approve` 给 AI；
- 搜索结果必须带状态、版本和证据；
- 默认优先返回 `APPROVED` 和 `VERIFIED`；
- `INFERRED` 必须明显标记。

### 17.3 Evidence 工具

```text
evidence.register_document
evidence.record_observation
evidence.attach_to_claim
evidence.get_redacted_view
evidence.verify_hash
```

约束：

- 原始证据保存在客户本地；
- 工具返回最少必要内容；
- 敏感证据默认返回脱敏视图；
- 每次访问有审计记录。

### 17.4 Probe 工具

```text
probe.check_connectivity
probe.invoke_http
probe.query_readonly
probe.inspect_contract
probe.compare_response
probe.check_authentication
```

约束：

- 必须携带批准的 `probe_plan_id`；
- 工具只能执行计划中列出的操作；
- 不接受 AI 提供的任意完整 URL 绕过目标引用；
- 凭据只接受 `credential_ref`；
- 所有响应必须有大小和时间限制。

### 17.5 Test 工具

```text
test.generate_candidate
test.validate_fixture
test.run_approved_case
test.compare_contract
test.record_result
```

### 17.6 Report 工具

```text
report.build_draft
report.validate_completeness
report.freeze_version
report.export_local
```

### 17.7 Binding 工具

```text
binding.build_draft
binding.validate_against_report
binding.publish_after_approval
binding.mark_stale
```

`binding.publish_after_approval` 必须由确定性权限判断执行，不能仅凭 AI 文本决定。

### 17.8 工具结果通用结构

建议所有工具结果包含：

```json
{
  "ok": true,
  "status": "VERIFIED",
  "summary": "",
  "data": {},
  "evidence_refs": [],
  "warnings": [],
  "next_questions": [],
  "error": null
}
```

失败时不得返回伪造的空成功结果。

## 18. 官方卡带设计

### 18.1 官方卡带包含什么

- 接入项目引导流程；
- 需求能力提取；
- 负责人问题生成；
- 现有知识查询；
- 最小探测计划生成；
- MCP 工具编排；
- 候选知识生成；
- 差异和冲突分析；
- 测试用例生成；
- 报告生成；
- 审批节点；
- 绑定草案生成。

### 18.2 官方卡带不包含什么

- 客户凭据；
- 客户接口地址；
- 客户原始日志；
- 客户业务数据；
- 客户私有字段字典；
- 客户项目知识；
- 未经授权的厂商私有资料。

### 18.3 建议 Flow

```text
开始接入项目
  -> 读取业务能力需求
  -> 查询客户本地已有知识
  -> 导入负责人提供的资料
  -> 生成第一轮问题
  -> 负责人回答与确认结构化结果
  -> 生成接口候选
  -> 生成最小探测计划
  -> 人工批准探测计划
  -> 执行只读探测
  -> 比较声明、文档和真实结果
  -> 生成第二轮差异问题
  -> 生成测试用例
  -> 执行批准的验证测试
  -> 形成候选知识
  -> 生成探测报告
  -> 负责人验收
  -> 生成正式绑定
  -> 结束
```

### 18.4 卡带升级

官方卡带升级只能升级方法、模板和安全规则，不能自动迁移或改变客户已批准知识。升级后需要运行兼容性检查。

### 18.5 卡带签名

正式环境只允许安装由可信来源签名的官方接入验证卡带。修改过的版本必须使用客户自己的签名身份并重新审批权限。

## 19. 相似接口的知识复用

### 19.1 复用公式

```text
接口家族模板
+ 客户本地已验证共同规则
+ 当前接口差异
= 当前接口候选契约
```

### 19.2 共同模式提取

当同一项目中十个接口具有相似结构时，可以识别：

- 相同认证方式；
- 相同请求头；
- 相同错误外壳；
- 相同分页结构；
- 相同成功码；
- 相同公共字段；
- 相同限流行为。

这些内容先成为“接口家族候选规则”，经过多个接口验证后才能成为项目内正式模板。

### 19.3 差异优先验证

对第十个相似接口，不重复完整询问，而是：

1. 套用项目内已验证模板；
2. 自动列出未覆盖字段；
3. 验证公共成功和错误结构；
4. 验证该接口独有副作用；
5. 只向负责人询问差异和未知项。

### 19.4 不允许错误继承

以下内容不得仅因接口相似就自动继承：

- 写入幂等性；
- 删除和撤销语义；
- 审批权限；
- 金额、库存和支付字段；
- 敏感数据分类；
- 自动重试策略；
- 补偿方式；
- 生产写入许可。

### 19.5 跨客户复用

跨客户只能复用：

- 官方通用方法；
- 合法公开产品资料；
- 无法识别客户的抽象模式；
- 客户明确授权贡献的脱敏模板。

默认禁止把客户 A 的原始知识用于客户 B。

## 20. 探测报告设计

### 20.1 报告首页

- 接入项目；
- 业务目标；
- 目标系统；
- 涉及接口数量；
- 报告版本；
- 验证环境；
- 总体结论；
- 是否建议上线；
- 负责人和审批人。

### 20.2 范围声明

明确说明：

- 本次检查了什么；
- 本次没有检查什么；
- 使用了哪些权限；
- 是否触碰生产环境；
- 是否执行写入测试；
- 报告不能证明什么。

### 20.3 接口明细

每个接口至少展示：

- 用途；
- 方法和目标引用；
- 认证；
- 输入契约；
- 输出契约；
- 字段字典；
- 分页和限流；
- 错误结构；
- 副作用；
- 幂等性；
- 验证等级；
- 证据；
- 未知项；
- 上线建议。

### 20.4 差异与冲突

单独列出：

- 文档与真实响应不一致；
- 负责人说法与测试结果不一致；
- 同类接口之间结构不一致；
- 不同环境之间不一致；
- 尚未解决的冲突。

### 20.5 测试结果

展示：

- 已执行用例；
- 未执行用例及原因；
- 通过、失败和跳过数量；
- 生产风险；
- 清理和补偿结果。

### 20.6 知识可信度

报告不能只给一个总分。必须逐项显示可信状态和证据。

### 20.7 上线门槛

报告明确给出：

```text
允许上线
有条件允许上线
禁止上线
等待负责人补充
等待重新测试
```

### 20.8 报告不可变

提交审批的报告版本必须冻结。后续修改生成新版本，旧版本用于审计和绑定追溯。

## 21. 审批、验收和正式绑定

### 21.1 接入项目状态

```text
DRAFT
  -> WAITING_FOR_OWNER
  -> READY_FOR_PROBE
  -> PROBE_APPROVED
  -> PROBING
  -> VALIDATING
  -> REPORT_REVIEW
  -> APPROVED
  -> BINDING_PUBLISHED
  -> ACTIVE
```

异常分支：

```text
NEEDS_INFORMATION
BLOCKED
REJECTED
STALE
REVALIDATING
```

### 21.2 报告批准条件

最少满足：

- 当前业务目标涉及的接口全部有结论；
- 所有关键字段有明确含义或明确未知处理；
- 所有高风险操作有策略；
- 验证等级符合业务风险；
- 测试失败没有被隐藏；
- 未知项不会导致不可接受的生产风险；
- 负责人确认结构化结果；
- 报告已冻结版本。

### 21.3 正式绑定发布条件

- 关联已批准报告；
- 固定输入输出 Schema；
- 固定映射版本；
- 固定凭据引用，不包含明文凭据；
- 固定允许的操作和环境；
- 固定重试、超时和幂等策略；
- 固定受影响的测试集；
- 记录批准者和有效期。

### 21.4 业务卡带使用规则

业务卡带只声明能力角色：

```text
需要：approval_task_query
```

部署时由正式绑定解析为：

```text
客户 OA Connector
  -> GET /api/tasks
  -> 输入映射 v3
  -> 输出映射 v2
  -> 凭据引用 oa-readonly-prod
  -> 策略 approval-query-policy-v1
```

业务卡带不得绕过绑定直接调用客户接口。

## 22. 正式运行后的反馈闭环

### 22.1 正式运行不会自动改写知识

运行时发现只进入观察区：

- 新错误码；
- 新字段；
- 字段缺失；
- 类型变化；
- 响应耗时变化；
- 契约不匹配；
- 认证变化。

### 22.2 自动处理范围

可以自动：

- 记录差异；
- 关联受影响知识；
- 运行无副作用回归测试；
- 生成变更摘要；
- 提醒负责人；
- 暂停明显不安全的绑定。

不能自动：

- 修改正式字段映射；
- 改变写入语义；
- 扩大权限；
- 接受新证书或新主机；
- 用新观察覆盖批准结论；
- 把生产响应作为 Prompt 指令执行。

### 22.3 减少负责人重复回答

再次询问负责人前，系统必须：

1. 搜索项目正式知识；
2. 搜索相似接口模板；
3. 检查历史回答；
4. 检查是否可通过低风险测试确定；
5. 只生成仍然无法确定的问题。

## 23. 版本变化与重新验证

### 23.1 触发条件

- 客户系统版本变化；
- 接口地址或认证变化；
- 请求或响应 Schema 变化；
- 正式测试连续失败；
- 新错误码超过阈值；
- 负责人主动标记知识过期；
- 凭据权限变化；
- 长时间未验证且风险较高。

### 23.2 影响分析

变化发生后需要回答：

- 哪些知识项受影响；
- 哪些绑定受影响；
- 哪些卡带部署受影响；
- 是否需要暂停生产执行；
- 哪些测试需要重跑；
- 是否需要负责人重新确认。

### 23.3 增量重新验证

只重新验证变化影响的内容，不重复整个接入流程。

## 24. 安全、隐私与合规边界

### 24.1 数据所有权

客户系统知识和探测结果归客户所有。客户应能够：

- 查看；
- 导出；
- 备份；
- 删除；
- 配置保留期限；
- 禁止厂商访问。

### 24.2 凭据

- 凭据只保存在客户本地凭据库；
- 卡带和报告只保存凭据引用；
- AI 不得看到明文凭据；
- 探测优先使用临时、只读、最小权限账号；
- 凭据需要轮换和失效机制。

### 24.3 日志与样例

- 默认脱敏手机号、身份证、姓名、邮箱、地址、订单号等；
- 支持只保存 Schema 和哈希；
- 完整响应按最短必要期限保留；
- 报告中避免展示原始业务正文；
- 技术支持包由客户主动生成和批准。

### 24.4 Prompt Injection

接口文档、日志、响应和负责人上传文件都属于不可信输入。其中的文字不能改变系统权限、工具白名单和审批规则。

### 24.5 网络

- 运行器默认主动连接本地管理器或使用内部网络；
- 不要求客户把旧系统暴露到公网；
- 探针目标使用白名单；
- 支持代理、mTLS 和客户证书；
- 对 DNS 变化和重定向做策略限制。

### 24.6 审计

必须记录：

- 谁提出了什么问题；
- 谁提供了什么回答；
- AI 如何结构化回答；
- 谁批准了探测计划；
- 探针调用了什么；
- 使用什么工具和卡带版本；
- 产生了什么证据和结论；
- 谁批准了报告和绑定。

## 25. 最小权限与未来企业权限体系

### 25.1 第一版最小权限

第一版不需要完整 RBAC，但必须支持：

- 项目创建者；
- 接口负责人邀请；
- 临时访问身份；
- 探测计划批准人；
- 接口和方法白名单；
- 只读凭据引用；
- 报告审批人；
- 操作审计。

### 25.2 不得推迟的权限判断

以下判断不能以“未来再做 RBAC”为理由省略：

- 当前用户是否能查看接口资料；
- 当前卡带是否能调用探针工具；
- 当前探测计划是否已批准；
- 当前目标是否在白名单；
- 当前凭据是否允许该操作；
- 当前报告是否由有权人员批准；
- 当前绑定是否允许生产使用。

### 25.3 后续扩展

真实企业需求出现后再扩展：

- 组织和部门；
- 多角色分权；
- RBAC/ABAC；
- 多级审批；
- 临时授权；
- 职责分离；
- 高风险双人批准；
- 数据分级和地域策略。

## 28. 错误处理与恢复

### 28.1 错误分类

```text
INFORMATION_MISSING       缺少负责人信息
AUTHENTICATION_FAILED     认证失败
AUTHORIZATION_DENIED      权限不足
TARGET_UNREACHABLE        目标不可达
POLICY_BLOCKED            被白名单或策略阻止
CONTRACT_MISMATCH         契约不匹配
RESPONSE_TOO_LARGE        响应超过限制
RATE_LIMITED              外部系统限流
SIDE_EFFECT_UNCERTAIN     副作用结果不确定
EVIDENCE_CONFLICT         证据冲突
OWNER_REJECTED            负责人拒绝
APPROVAL_EXPIRED          探测批准已过期
```

### 28.2 重试原则

- 可达性临时失败可以有限重试；
- 认证失败不自动高频重试；
- 权限不足不通过更换或扩大凭据绕过；
- 写入超时默认禁止自动重试；
- 限流遵守服务端退避信息；
- 所有重试次数有硬上限。

### 28.3 恢复

长流程使用检查点保存：

- 已确认问题；
- 已批准计划；
- 已完成探测；
- 已形成证据；
- 等待负责人项目。

恢复时不得重复执行可能产生副作用的操作，除非已证明幂等或获得重新批准。

## 29. 最小可用版本范围

### 29.1 必须实现

第一版只支持一个真实接入项目闭环：

- 一张官方接口接入验证卡带；
- 一个客户本地运行器；
- 一个本地 MCP 服务；
- 一个结构化本地知识库；
- HTTP/REST 接口；
- API Key 或固定 Token 凭据引用；
- 接口负责人问答；
- 只读探测；
- JSON 请求与响应 Schema；
- 候选知识与正式知识分离；
- 探测报告；
- 人工批准；
- 一个正式连接绑定；
- 一张普通业务卡带成功使用绑定。

### 29.2 建议第一个场景

优先选择：

- 单一客户；
- 单一系统；
- 一名明确接口负责人；
- 三到十五个相似的只读接口；
- 一个可量化业务结果；
- 不涉及支付、审批写入和删除；
- 有测试环境或可控生产只读查询。

### 29.3 第一版不实现

- SOAP、JDBC、消息队列同时支持；
- 自动跨客户模板学习；
- 全量向量知识库；
- 完整企业 RBAC；
- 复杂多级审批；
- 自动写入验证；
- 完整离线安装平台；
- 接口市场；
- 自动生成任意连接器代码；
- 无人值守批准。

## 30. 分阶段行动计划

### 阶段 0：获取真实场景

目标：在写大量底层代码前，拿到真实接入证据。

行动：

- 找到一个真实客户或合作方；
- 明确一个具体扩展功能；
- 确认一名真正使用过接口的负责人；
- 收集三到十五个相关接口的脱敏资料；
- 手工走一遍问答和验证流程；
- 记录哪些信息确实反复出现。

完成标准：能够用人工方式形成一份客户认可的接入报告。

### 阶段 1：固定最小契约

目标：定义必要结构，不提前设计万能协议。

行动：

- 定义接入项目；
- 定义问题和回答；
- 定义探测计划；
- 定义证据；
- 定义知识状态；
- 定义报告；
- 定义正式绑定；
- 定义错误信封。

完成标准：同一份数据可以驱动界面、运行器和报告。

### 阶段 2：实现本地受控探针

目标：运行器能够执行最小只读验证。

行动：

- 实现目标白名单；
- 实现凭据引用；
- 实现 HTTP 只读调用；
- 实现响应大小、超时和重试限制；
- 实现 Schema 提取；
- 实现证据脱敏和审计；
- 实现真实错误分类。

完成标准：探针无法访问计划外地址，失败不会伪装成功。

### 阶段 3：实现官方卡带闭环

目标：负责人能够通过卡带完成问答、探测和报告。

行动：

- 读取业务需求；
- 查询本地知识；
- 生成问题；
- 接收负责人回答；
- 生成探测计划；
- 等待批准；
- 调用 MCP 工具；
- 生成候选知识；
- 生成报告；
- 等待验收。

完成标准：完整过程不需要研发人员手工修改数据库状态。

### 阶段 4：生成并使用正式绑定

目标：验证接入结果能够真正服务业务卡带。

行动：

- 从批准报告生成绑定草案；
- 固定映射和策略；
- 发布绑定；
- 让普通业务卡带通过能力角色使用绑定；
- 记录正式运行观察；
- 模拟接口变化并触发重新验证。

完成标准：业务卡带不接触具体客户地址和凭据。

### 阶段 5：验证相似接口复用

目标：证明负责人不需要重复回答相同问题。

行动：

- 用第一批接口形成项目内模板；
- 接入第二批相似接口；
- 比较提问数量；
- 比较人工耗时；
- 检查是否出现错误继承；
- 只固化真实重复出现的能力。

完成标准：相似接口接入时间明显下降，同时没有降低关键验证要求。

### 阶段 6：再建设企业治理

只有前述闭环在真实项目中成立后，再逐步建设：

- Java/Spring Boot 统一管理器；
- 组织和租户；
- 完整 RBAC/ABAC；
- 多运行器调度；
- 版本发布和回滚；
- 集中审计；
- 配额、成本和 SLA；
- 完全私有化交付。

## 31. 验收标准

### 31.1 产品验收

- 负责人能够理解系统提出的问题；
- 负责人可以明确回答“不知道”；
- 系统不会重复询问已经批准的问题；
- 报告清楚区分声明、观察、推断和验证；
- 报告清楚展示未检查范围；
- 批准前业务卡带无法使用接口；
- 批准后可以生成可追溯绑定。

### 31.2 安全验收

- 探针不能访问白名单外目标；
- 明文凭据不进入卡带、日志和报告；
- 未批准的写入调用被阻止；
- 大响应和长时间请求被限制；
- 外部文本无法改变工具权限；
- 客户项目知识不离开客户本地；
- 所有关键操作可审计。

### 31.3 知识验收

- 正式知识有来源和证据；
- 候选知识不能影响生产绑定；
- 修改正式知识产生新版本；
- 冲突不会被静默覆盖；
- 相似接口复用仍然执行差异验证；
- 系统变化可以把绑定标记为过期。

### 31.4 运行验收

- 普通业务卡带通过能力角色调用绑定；
- 运行器返回真实错误；
- 只读调用可以安全有限重试；
- 写入超时不会盲目重试；
- 运行观察只进入候选区；
- 接口契约变化能够触发告警或暂停。

## 32. 测试策略

### 32.1 单元测试

- 知识状态转换；
- 探测计划策略校验；
- 白名单匹配；
- 凭据引用解析；
- Schema 比较；
- 脱敏；
- 报告完整性；
- 绑定发布门槛。

### 32.2 集成测试

- 官方卡带调用 MCP；
- MCP 调用测试接口；
- 证据写入本地知识库；
- 报告引用证据；
- 审批后发布绑定；
- 业务卡带使用绑定。

### 32.3 安全测试

- Prompt Injection 文档；
- URL 重定向绕过；
- DNS 变化；
- 大响应体；
- 慢请求；
- 凭据泄漏；
- 未批准写操作；
- 路径穿越；
- 越权读取其他项目知识。

### 32.4 行为测试

- 负责人回答正确；
- 负责人回答错误；
- 负责人回答不确定；
- 文档和接口冲突；
- 十个接口九个相似、一个特殊；
- 接口升级后 Schema 变化；
- 生产运行出现新错误码；
- 报告被拒绝后重新验证。

### 32.5 真实客户验收

必须由真实接口负责人完成至少一次完整流程。内部研发人员模拟负责人不能替代此项证据。

## 33. 产品指标

第一阶段不以“扫描多少接口”作为主要指标。建议观察：

- 从项目开始到报告批准的时间；
- 负责人实际投入时间；
- 首次问答数量；
- 相似接口接入时减少的问题数量；
- 自动生成结论中被负责人修改的比例；
- 文档与真实接口行为的冲突数量；
- 上线前发现的高风险问题数量；
- 正式运行后的契约失败率；
- 需要重新询问负责人的次数；
- 知识复用节省的接入时间；
- 未经批准的探测被阻止次数。

真正需要证明的是：

```text
在不降低安全和验证要求的情况下，
相似接口越接越快，
负责人重复解释越来越少，
人员变动后知识仍然可用。
```

## 34. 典型 OA 接入示例

### 34.1 业务需求

客户希望新增“审批超时日报”，每天统计超时未处理流程并推送给部门负责人。

### 34.2 所需能力

```text
人员查询
部门查询
待办审批查询
流程详情查询
工作日或超时规则查询
```

### 34.3 负责人已知信息

- OA 有内部 REST 接口；
- 使用固定 Token；
- 待办接口由旧移动端使用过；
- `state=2` 可能代表处理中；
- 接口分页方式与其他接口相似；
- 工作日规则可能存放在另一个模块。

### 34.4 第一轮问题

- 移动端当前是否仍在调用该接口？
- Token 使用应用身份还是用户身份？
- `state` 有哪些已知值？
- 超时按自然日还是工作日？
- 部门负责人从哪个字段获取？
- 是否有测试账号和脱敏样例？

### 34.5 最小探测

- 使用测试 Token 查询一个测试用户；
- 查询固定一天的待办；
- 验证空结果；
- 验证错误 Token；
- 验证分页第二页；
- 比较三个相似查询接口的公共外壳；
- 不扫描其他 OA 模块；
- 不执行任何审批写入。

### 34.6 候选知识

```text
声明：state=2 表示处理中
来源：接口负责人
状态：DECLARED

观察：12 条未完成记录均为 state=2
来源：测试环境响应
状态：OBSERVED

推断：state=2 可以用于筛选未完成审批
状态：INFERRED

补充测试：构造一条已完成流程进行比较
结果：已完成记录为 state=3
状态：VERIFIED

负责人确认：允许用于日报筛选
状态：APPROVED
```

### 34.7 报告结论

- 四个只读接口通过 L2 测试；
- 分页和空结果已验证；
- 工作日规则尚未确认；
- 第一版日报暂按自然日计算并明确标注；
- 不允许执行审批写入；
- 负责人批准后生成四个查询操作绑定。

### 34.8 后续相似接口

接入第六个查询接口时，系统复用已经验证的认证、分页和错误外壳，仅询问新字段含义并验证独有响应结构。

## 35. 主要风险与对应措施

### 35.1 负责人记忆错误

措施：回答只进入 `DECLARED`，使用样例和测试验证。

### 35.2 AI 过度自信

措施：强制状态、证据和置信来源；推断不得直接批准。

### 35.3 相似接口错误继承

措施：共同模板加差异验证；副作用和高风险字段禁止自动继承。

### 35.4 探测范围膨胀

措施：所有操作必须对应当前能力需求并进入批准计划。

### 35.5 客户数据泄漏

措施：本地存储、凭据引用、脱敏、默认禁止上传、外部模型调用显式授权。

### 35.6 变成定制外包

措施：只沉淀重复出现的通用对象、工具和模板；业务差异留在客户本地知识和绑定中。

### 35.7 知识库再次过期

措施：版本、有效期、运行契约检查和增量重新验证。

### 35.8 Mock 造成虚假信心

措施：报告强制展示验证等级，L1 不得宣称生产通过。

### 35.9 写入操作造成事故

措施：第一版只读；未来写入需要幂等、Dry Run、人工确认和补偿策略。

### 35.10 完整权限体系拖慢闭环

措施：先实现项目级最小授权，但不省略白名单、批准和审计。

## 36. 明确暂缓的事项

在第一个真实项目成功前，暂缓：

- 为所有 ERP/OA 产品建立预置知识；
- 自动扫描整个客户系统；
- 复杂知识图谱；
- 跨客户联邦学习；
- 完整企业数据目录；
- 自动反编译旧系统；
- 任意数据库写入；
- 自动生产审批；
- 连接器市场；
- 微服务拆分；
- 大规模消息中间件；
- Kubernetes 多集群管理；
- 完整 Java 企业控制面重写。

这些能力只能由真实项目中的重复需求触发，不能因为“企业版以后可能需要”而提前建设。

## 37. 尚待真实项目决定的问题

以下问题暂不预设最终答案：

- 第一批真实接口是 REST、数据库还是其他协议；
- 本地知识库存储使用现有运行时存储还是独立服务；
- 负责人交互主要位于 Lite、企业管理器还是独立受限页面；
- 官方卡带与客户项目知识的具体协议边界；
- 哪些观察可以自动晋升为 `VERIFIED`；
- 报告审批是否需要接口负责人和系统负责人双签；
- 项目内接口模板如何表达继承和覆盖；
- 正式绑定是否建立独立协议版本；
- 本地模型与外部模型如何按数据分类路由；
- 多运行器环境下知识库和证据如何一致；
- 客户如何安全导出、迁移和销毁项目知识；
- 第一个行业应从 OA、ERP、CRM 还是其他系统切入。

决策方法：优先观察第一个真实项目的工作过程，再固定最小公共语义。

## 38. 术语表

| 术语 | 含义 |
|---|---|
| 接口接入验证卡带 | 官方维护的系统卡带，组织负责人交互、最小探测、测试、报告、审批和绑定生成 |
| 体检卡带 | 接口接入验证卡带的团队内部通俗称呼，不代表全量扫描 |
| 探针 | 运行器内部受策略限制的确定性检查能力 |
| 接口负责人 | 掌握目标接口历史用法、字段或系统行为的客户人员 |
| 接入项目 | 围绕一个明确业务目标进行的一次有限接口接入工作 |
| MCP | 卡带访问客户本地知识和探测工具的标准工具接口，不是知识库本身 |
| 候选知识 | 新观察、负责人声明或 AI 推断，尚未批准用于生产 |
| 正式知识 | 经过验证和负责人批准、可以支持正式绑定的知识 |
| 证据 | 支持或反驳知识声明的文档、样例、日志、测试或真实行为记录 |
| 探测计划 | 明确目标、操作、数据范围、风险和批准记录的最小检查计划 |
| 探测报告 | 对范围、证据、测试、未知项、风险和上线建议的冻结版本总结 |
| Connector Binding | 业务卡带能力角色与客户具体接口、映射、凭据引用和策略之间的正式绑定 |
| 验证等级 | L0 文档、L1 仿真、L2 测试环境、L3 生产只读、L4 生产受控写入 |
| 接口家族模板 | 在合法边界内沉淀的相似接口共同规则，用于减少重复提问 |
| STALE | 知识或绑定可能因系统变化而过期，需要重新验证 |

## 最终行动结论

当前团队不应立即开发一个庞大的企业体检平台，也不应在没有真实客户前设计全量接口知识体系。

第一步应该是找到一个真实扩展需求和一名真正使用过相关接口的负责人，人工验证本文流程；随后只实现支撑该流程所需的最小官方卡带、运行器探针、MCP 工具、本地知识和审批绑定能力。

产品成功的第一项证据不是“AI 扫描了多少系统”，而是：

```text
负责人只解释一次，
系统用真实测试把知识固定下来，
相似接口不再重复从零沟通，
正式运行只使用已经验证和批准的连接绑定，
客户知识始终保存在客户自己的环境中。
```
