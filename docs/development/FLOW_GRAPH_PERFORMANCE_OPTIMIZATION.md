# 大型 Flow 画布性能优化方案

> 状态：P0/P2 首轮优化已实施，待大型 Flow 压测
> 排查基线：2026-07-27
> 适用范围：设计台成果视图、工程视图及其共用的 React Flow 画布
> 目标：在不改变 Flow 协议、卡带数据和现有交互语义的前提下，消除节点数量增长带来的非必要重复计算与全量重渲染。

## 1. 结论

大型 Flow 的卡顿主要发生在前端画布层，不是后端执行器或卡带解析器造成的。当前节点渲染并非只处理节点自己的数据：每个工程节点都会重复扫描全部连线、全部工程关系和源码文件；选择、运行状态或显示配置变化时，又可能让整张画布重新生成节点渲染器和节点数据。

当边数随节点数同步增长时，主要计算接近：

```text
当前：O(N * E + N * R + N * S)
目标：O(N + E + R + S) 的一次预处理 + 可视节点的局部渲染
```

- `N`：节点数
- `E`：流程边数
- `R`：工程数据关系数
- `S`：卡带源码总量

这意味着小型示例不明显，但节点增加后，拖拽、点选、缩放和切换状态会一起变慢。

## 2. 已确认的瓶颈

### 2.1 每个工程节点重复构建全局视图

涉及文件：

- `src/frontend/src/pages/flow-workbench/EngineeringNodeCard.tsx`
- `src/frontend/src/pages/flow-workbench/engineeringNode.ts`

当前 `EngineeringNodeCard` 在渲染期间调用 `buildEngineeringNodeView`，并多次对完整 `dataRelations` 执行 `filter`。`buildEngineeringNodeView` 和 `buildEngineeringSections` 又分别扫描完整 `graph.edges`，因此单个节点至少触发多次全边扫描。

同一过程中还会逐节点执行：

- 在全部卡带文件中定位节点源码；
- 对源文件切行并搜索节点 ID；
- 格式化完整节点 JSON；
- 计算输入、输出、依赖和控制关系。

影响：工程视图的计算量随节点和边共同增长，且产生大量短生命周期数组、字符串与 `Set`。

### 2.2 节点渲染器引用不稳定

涉及文件：`src/frontend/src/pages/flow-workbench/FlowGraphView.tsx`

`CustomNode` 闭包依赖选中节点、完整 `graph`、`files`、运行状态和工程关系等全局对象；`nodeTypes` 又依赖 `CustomNode`。选择一个节点或改变部分全局状态时，渲染器引用会变化，所有自定义节点都可能重新渲染。

工程节点卡目前没有组件级 memo。即使只有一个节点的选中态发生变化，其他节点仍可能重新进行全图分析。

### 2.3 工程视图执行了未使用的成果视图计算

`CustomNode` 在判断工程视图分支之前，会为当前节点过滤进入和离开的完整边集合。工程节点并不使用这部分结果，但每个节点仍会计算。

### 2.4 屏幕外节点仍被挂载

当前 React Flow 未启用 `onlyRenderVisibleElements`。项目使用的 `@xyflow/react 12.11.2` 已支持该属性，因此视口外节点目前也会参与 React 和 DOM 渲染。

该选项不能替代数据索引和 memo，但可以明显限制超大画布的同时挂载量。实施时需要验证小地图、框选、搜索定位、自动适配和连线显示行为。

### 2.5 已保存布局仍先执行自动布局

涉及文件：`src/frontend/src/pages/flow-workbench/nodeModel.ts`

`buildBalancedLayout` 先调用 `buildAutoAlignLayout`，之后才判断是否所有节点都已有保存坐标。因此打开已排版 Flow 时，Dagre 计算结果可能被直接丢弃。

碰撞处理还包含反复查找列和归并布局的逻辑，在节点较多时可能进一步放大成本。

### 2.6 全图派生数据重复生成

涉及文件：

- `src/frontend/src/pages/flow-workbench/views.tsx`
- `src/frontend/src/pages/flow-workbench/FlowGraphView.tsx`
- `src/frontend/src/pages/flow-workbench/nodeAuthoring.ts`

工程数据关系分别为统计和画布各构建一次。`views.tsx` 还会为每个可编辑节点生成 authoring path，其中部分判断再次扫描节点和边。工程视图不需要的成果编辑路径也可能提前计算。

### 2.7 节点与边存在一次状态镜像更新

`FlowGraphView` 先计算 `initialNodes`、`initialEdges`，再通过 effect 写入 React Flow 状态。图结构、布局或显示数据变化时，容易经历一次旧状态渲染和一次全量状态替换。

## 3. 优化原则

1. 全图分析只做一次，节点渲染只读取自己的切片。
2. 图结构变化与交互状态变化分开处理。选择节点不应重建图索引。
3. 渲染器、`nodeTypes` 和无变化节点的数据引用保持稳定。
4. 先减少计算和重渲染，再考虑动画、阴影等样式级微调。
5. 优化不得改变 Flow 文件结构、协议语义、运行顺序或保存结果。
6. 所有性能改造必须配套行为回归，不能用关闭工程信息或牺牲操作能力换取速度。

## 4. 分阶段实施

### P0：消除平方级重复计算

#### 4.1 建立统一的图分析索引

为一次 `graph/files` 版本生成共享索引，例如：

```ts
type FlowGraphIndex = {
  nodeById: Map<string, FlowNode>
  incomingByNode: Map<string, FlowEdge[]>
  outgoingByNode: Map<string, FlowEdge[]>
  relationsBySource: Map<string, EngineeringDataRelation[]>
  relationsByTarget: Map<string, EngineeringDataRelation[]>
  sourceByNode: Map<string, NodeSourceLocation | null>
}
```

索引只在图结构或源码文件实际变化时重建。`EngineeringNodeCard` 不再接收完整 `graph`、`files` 和全部关系，而是接收已经整理好的当前节点视图。

源码定位应逐文件扫描一次并生成 `nodeId -> source` 映射，避免每个节点重复切分同一文件。

#### 4.2 让节点卡成为纯局部组件

- 使用 `React.memo` 包装成果节点和工程节点卡；
- props 只包含节点自身展示所需的数据；
- 避免在 render 内创建可复用的大数组、对象和 `Set`；
- 运行状态按节点 ID 切片，不传入完整状态集合；
- 选中态变化时只更新上一个和当前选中的节点。

#### 4.3 稳定自定义节点类型

将 `nodeTypes` 提升为模块级常量，或确保其不依赖选择、文件和图对象。动态内容通过稳定的 `node.data` 或细粒度 store selector 提供。

不要让 `selectedNode` 进入全局节点渲染器闭包。React Flow 节点的 `selected` 字段或节点级选择订阅应作为唯一来源。

#### 4.4 移除分支前的无效计算

工程视图直接进入工程节点分支；成果视图才计算成果卡需要的进入边、离开边和摘要数据。两种视图共享索引，但不共享无关的展示计算。

### P1：限制实际渲染量与布局成本

#### 4.5 启用可视区域渲染

在 React Flow 上评估并启用：

```tsx
<ReactFlow onlyRenderVisibleElements />
```

重点回归：

- 缩放和平移后节点及时出现；
- 搜索定位和 `fitView` 正常；
- 框选跨越视口边界时行为符合预期；
- 连线、控制边和工程数据边不残缺；
- 小地图和节点数量统计不依赖 DOM 挂载数量。

如果框选必须覆盖未挂载节点，应使用 React Flow 的节点坐标数据计算命中范围，而不是查询 DOM。

#### 4.6 有完整坐标时跳过 Dagre

`buildBalancedLayout` 应先验证保存布局是否完整：

```text
完整且合法 -> 直接返回保存布局
缺失或非法 -> 运行自动布局与碰撞处理
```

自动整理按钮仍显式调用 Dagre，不受此快速路径影响。

#### 4.7 合并派生数据

- 工程关系统计复用画布已经生成的关系列表；
- authoring path 仅在成果视图或相关编辑器打开时生成；
- 节点 JSON 文本只在原始信息区域展开时生成；
- 大型详情数据按需计算，不进入所有节点的首屏渲染路径。

### P2：减少全量状态替换

#### 4.8 调整 React Flow 状态同步

避免以 `initialNodes -> effect -> setNodes` 方式镜像整张图。可选择：

- 由单一状态源直接管理 React Flow 节点；或
- 对新旧节点做 ID 级差异更新，仅替换发生变化的节点；或
- 图结构、布局、运行态、选中态分别进入不同更新通道。

需要保证拖拽中的临时位置不会被迟到的 effect 覆盖。

#### 4.9 高频事件降载

完成 P0/P1 后再分析以下事件：

- 节点拖拽中的保存与碰撞检查；
- 视口变化回调；
- 框选指针移动；
- 运行事件连续推送；
- 边高亮和动画状态。

只有确认证据后才加入节流或批处理，避免用延迟掩盖全量重算。

## 5. 性能基准方案

当前仓库示例最多只有 9 个节点，不能用于确定大型 Flow 的性能阈值。实施前应增加不进入用户数据目录的生成式测试夹具，至少覆盖：

| 规模 | 节点 | 边 | 用途 |
|---|---:|---:|---|
| 中型 | 100 | 150-250 | 日常开发基线 |
| 大型 | 300 | 500-900 | 主要优化目标 |
| 压力 | 1000 | 1500-3000 | 退化趋势与内存检查 |

每种规模同时覆盖成果视图和工程视图，并记录：

- 打开 Flow 到画布可交互的时间；
- 点击切换节点的主线程耗时；
- 连续拖拽节点时的帧率与最长任务；
- 缩放、平移和框选时的帧率；
- React commit 次数及单次 commit 时间；
- 实际挂载的节点 DOM 数量；
- 堆内存和临时对象分配趋势；
- 切换运行状态时实际重渲染的节点数量。

### 建议的首轮验收门槛

以下是专项开始时的工程目标，需在目标用户常见硬件上校准后固定：

- 300 节点下，选择节点的可感知响应不超过 100 ms；
- 单节点选中变化只重渲染必要节点，不触发全部节点卡 commit；
- 画布平移和缩放不持续出现超过 50 ms 的主线程长任务；
- 启用可视区域渲染后，DOM 节点数量主要随视口内容变化，而不是随总节点数线性增长；
- 已保存完整布局的 Flow 打开时不调用 Dagre；
- 100、300、1000 节点的派生数据构建时间呈近似线性增长。

这些门槛不是产品承诺；首次基准完成后，应根据实测硬件和卡片复杂度更新为稳定的回归阈值。

## 6. 验证工具与方法

1. 使用 React DevTools Profiler 检查一次选中操作涉及的组件和 commit。
2. 使用浏览器 Performance 面板记录打开、拖拽、缩放、框选和运行状态更新。
3. 在图索引、Dagre、关系构建和源码索引入口加入仅开发环境启用的计时标记。
4. 使用固定随机种子生成基准图，保证每次测试结构一致。
5. 性能测试前关闭开发者工具扩展等非项目脚本，并记录浏览器、CPU、内存和缩放比例。
6. 同一用例至少运行三次，分别记录冷启动和热启动结果。

## 7. 行为回归清单

性能优化完成后必须验证：

- 节点新增、删除、复制、连线和断线；
- 节点拖拽位置保存与重新打开；
- 自动整理、`fitView`、缩放和平移；
- 成果视图与工程视图切换；
- 控制边、数据边、依赖边的显示过滤；
- 节点选择、详情卫星卡和钉住状态；
- AI 管家指针定位与框选范围；
- 搜索或外部动作定位屏幕外节点；
- 节点运行中、成功、失败和恢复状态；
- 小地图、统计数字与真实图数据一致；
- 100% 和 125% 系统缩放下无裁切或错位。

## 8. 实施顺序与停止条件

建议按以下顺序提交，每一步单独测量：

1. 建立共享图索引和源码索引；
2. 改造工程节点 props，并加入 memo；
3. 稳定 `CustomNode` 和 `nodeTypes`；
4. 去除工程/成果分支的无效计算；
5. 为完整保存布局增加 Dagre 快速路径；
6. 启用并回归可视区域渲染；
7. 合并重复派生数据；
8. 根据 profiler 结果决定是否重构状态同步和高频事件。

每一步都必须保存优化前后数据。如果某项改造没有减少计算、commit 或长任务，应停止继续抽象并重新采样，避免仅凭代码形式判断性能。

## 9. 非目标

本专项暂不处理：

- 后端运行吞吐和远程模型调用延迟；
- 卡带加密、虚拟化壳和发布平台；
- 重新设计节点视觉或减少节点展示信息；
- 修改 Flow 协议和卡带文件格式；
- 用分页拆分用户原本需要同时观察的流程。

## 10. 当前验证状态

- 已建立工程节点共享索引，边、工程关系和源码定位从逐节点全量扫描改为按图版本一次预处理；
- 工程节点渲染器已稳定为模块级类型，节点卡使用 `React.memo`，详情栏复用画布已经生成的节点视图；
- 工程视图不再提前执行成果卡片计算，完整保存布局会直接跳过 Dagre；
- React Flow 改为内部维护拖动时的高频位置，仅在拖动结束时快照并保存布局，避免每个指针事件驱动父组件全量状态更新；
- 9 节点、20 边示例中，连续切换节点的点击到下一帧中位数由约 `28.2 ms` 降至约 `16.5 ms`，P95 由约 `32.1 ms` 降至约 `17.8 ms`；
- 无扩展浏览器中的 10 次拖动采样，项目脚本累计约 `10.0 ms`，约 `1.0 ms/事件`；用户浏览器中的主要剩余拖动开销来自翻译扩展内容脚本，画布已增加标准 `translate="no"` / `notranslate` 排除标记；
- `onlyRenderVisibleElements` 已实际评估，但当前示例的拖动耗时反而上升，因此本轮没有启用，待大型 Flow 夹具下重新验证；
- 现有前端生产构建和运行时错误测试通过；
- 因仓库缺少大型 Flow 测试夹具，尚未形成真实节点规模与帧率、交互延迟之间的量化曲线；
- 当前数据只证明首轮架构优化和小型示例没有回退，正式生产前仍需补充 100/300/1000 节点基准与行为回归。
